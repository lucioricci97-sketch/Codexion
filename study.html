1. What is Codexion

Codexion is a multithreaded simulation from the 42 curriculum. It models N coders sharing N USB dongles around a round table. A coder needs two dongles at once to compile their code. After compiling they debug, then refactor, then start over.

If a coder doesn't start a new compile within time_to_burnout milliseconds of starting the previous one, they burn out and the simulation stops. The simulation also stops normally when every coder reaches n_required compiles.

Why this project exists

It's the classic Dining Philosophers problem with new names. It teaches: POSIX threads, mutexes, condition variables, fair scheduling, deadlock prevention, and precise timing — the fundamentals of concurrent programming.

Command line

./codexion n_coders t_burnout t_compile t_debug t_refactor n_required t_cooldown {fifo|edf}

All times are in milliseconds. Scheduler is exactly fifo or edf.

What the output looks like

0 1 has taken a dongle
1 1 has taken a dongle
1 1 is compiling
201 1 is debugging
401 1 is refactoring
402 2 has taken a dongle
...
1204 3 burned out

Format: timestamp_in_ms coder_id action. Time is relative to simulation start.

2. The problem (visual)

With N = 5, the setup looks like this. The dongles sit on the table between neighbors. Each coder must grab the dongle on their left and the dongle on their right to compile.

● Coder   ▭ Dongle. Coder C1 shares D0 with C2 and D4 with C5. To compile, C1 must hold both D0 and D4.

What can go wrong

Deadlock

Every coder grabs the dongle on their right and waits forever for the one on their left. Nobody can compile. The simulation freezes. Burnout cascades.

Starvation

Two greedy coders monopolize a dongle. The unlucky third coder never gets a turn and eventually burns out even though the system isn't deadlocked.

Race conditions

Two coders read available = 1 at the same time and both decide to take the dongle. Same physical dongle in two hands at once. Invalid state.

Interleaved logs

Two threads printf simultaneously and produce 123 1 is com2 has taken a dongle\npiling\n. Unreadable output, automatic fail.

3. POSIX threads cheat sheet

The whole project uses 6 building blocks. Master these and the rest is plumbing.

Thread

pthread_t t;
pthread_create(&t, NULL, my_function, my_argument);
/* my_function runs in parallel with the caller */
pthread_join(t, NULL);  /* wait for it to finish */

A thread is an independent execution path inside the same process — all threads share memory. my_function has signature void *(*)(void *): it takes a void* in, returns a void* out.

Mutex (mutual exclusion lock)

pthread_mutex_t m;
pthread_mutex_init(&m, NULL);
pthread_mutex_lock(&m);     /* blocks if someone else holds m */
/* critical section: read/write shared state safely here */
pthread_mutex_unlock(&m);
pthread_mutex_destroy(&m);

Only one thread at a time can hold a given mutex. If two threads access shared state and at least one of them writes, the access must be protected by a mutex or you have a race condition.

Condition variable

pthread_mutex_t m;  pthread_cond_t  c;

/* WAITER */
pthread_mutex_lock(&m);
while (!condition)              /* always while, never if */
    pthread_cond_wait(&c, &m); /* atomically unlock + sleep, relock on wake */
/* condition is true here */
pthread_mutex_unlock(&m);

/* SIGNALER */
pthread_mutex_lock(&m);
condition = 1;
pthread_cond_broadcast(&c);    /* wake all waiters */
pthread_mutex_unlock(&m);

Why while and not if?

Three reasons:
  1. Spurious wakeups — the OS can wake your thread for no reason.
  2. Stolen wakeups — another waiter raced you and consumed the resource.
  3. The condition could have flipped back to false between signal and wakeup.
Always re-check the condition after waking up.

Cond timedwait

struct timespec ts;     /* ABSOLUTE wall-clock time, not delta */
pthread_cond_timedwait(&c, &m, &ts);

Like cond_wait but wakes automatically at the given wall-clock instant. We use it when a coder is "next in line" for a dongle but the dongle is still in cooldown — we sleep exactly until cooldown ends.

Time

struct timeval tv;
gettimeofday(&tv, NULL);
long us = tv.tv_sec * 1000000L + tv.tv_usec;  /* microseconds since 1970 */

We work in microseconds internally for precision and divide by 1000 only when printing. The 64-bit long on Linux x86_64 fits microseconds since epoch with hundreds of years to spare.

Sleep

usleep(500);  /* sleep at least 500 microseconds */

The unit is microseconds, not milliseconds. We never use it for "the right" amount of time — we sleep in small chunks (500 µs) inside a loop that also checks the stop flag.

4. Deadlock & how we avoid it

Coffman's four conditions

A deadlock requires all four of these to hold at the same time:

ConditionMeaningCan we remove it?
Mutual exclusionA dongle can't be shared.No — it's the whole problem.
Hold and waitA coder holds one dongle while waiting for the other.Hard — the subject implies it.
No preemptionYou can't snatch a dongle from someone.No — would be unfair.
Circular waitC1 waits for C2 who waits for C3 ... who waits for C1.YES. We break this one.

The fix: resource hierarchy

Every coder always grabs the lower-numbered dongle first.

Look at init.c → assign_neighbors. For every coder it stores low = min(left, right) and high = max(left, right). The acquisition order is always low first, high second. That single rule kills the cycle.

5. FIFO vs EDF

Resource hierarchy stops deadlock but doesn't ensure fairness. Without a scheduler, a fast neighbor could keep beating you to every dongle. The subject mandates a fair arbitration policy — either FIFO or EDF. Both use the same data structure (a priority queue per dongle) with a different sort key.

FIFO — First In, First Out

Key = now_us() when the request is registered.

Older request wins. Strictly fair by arrival time. Simple.

Pro: deterministic and easy to reason about.
Con: doesn't help endangered coders catch up.

EDF — Earliest Deadline First

Key = last_compile + t_burnout (microseconds).

The coder closest to burnout wins. Optimal for real-time deadlines.

Pro: proven liveness — no starvation under feasible parameters.
Con: equal deadlines need a tiebreaker (we use arrival order implicitly via heap insertion).

The whole switch is one function:

static long pick_key(t_coder *c)
{
    if (c->sim->args.scheduler == EDF)
    {
        pthread_mutex_lock(&c->mtx);
        long last = c->last_compile;
        pthread_mutex_unlock(&c->mtx);
        return (last + (long)c->sim->args.t_burnout * 1000L);
    }
    return (now_us());
}

6. The heap (priority queue)

The subject requires you to implement a priority queue yourself (no STL). For each dongle, only two coders can ever compete (the two neighbors), so the heap is fixed at size 2. The implementation is still a real binary min-heap with bubble-up / sift-down — it just happens to be small.

When the dongle becomes free, every waiting coder is broadcast-woken. Each one checks heap_top(&d->queue) == my_id. The one at the top wins; everyone else goes back to cond_wait.

Why a custom atoi?

The standard atoi silently returns 0 for "abc". We need to reject anything that isn't a clean positive integer — including overflow. long n lets us detect the overflow before it truncates to int.

Two loggers, on purpose

log_state respects the stop flag — it refuses to print "is debugging" after the simulation has stopped. force_log ignores the stop flag because the burned out message itself must always go out.

Why precise_sleep?

A plain usleep(200000) would block for 200 ms even after the monitor announced burnout. Our loop wakes every 500 µs to re-check the stop flag, so coders exit promptly.

.c heap.c — the priority queue 
#include "codexion.h"


static int req_less(const t_request *a, const t_request *b) {
    if (a->key != b->key) return (a->key < b->key);
    return (a->id < b->id);   /* tie-breaker — required for deterministic EDF */
}

static void bubble_up(t_heap *h, int i)
{
    int parent;
    t_request tmp;
    t_request tmp;
    while (i > 0) {
        parent = (i - 1) / 2;
        if (req_less(&h->items[i], &h->items[parent])) {
            swap_req(&h->items[i], &h->items[parent]);
            i = parent;
        } else break ;
    }
}

static void sift_down(t_heap *h, int i)
{
    int left, right, smallest;
    t_request tmp;
    t_request tmp;
    while (1) {
        left = i * 2 + 1;
        right = i * 2 + 2;
        smallest = i;
        if (left  < h->size && req_less(&h->items[left ], &h->items[smallest])) smallest = left;
        if (right < h->size && req_less(&h->items[right], &h->items[smallest])) smallest = right;
        if (smallest == i) break ;
        swap_req(&h->items[smallest], &h->items[i]);
        i = smallest;
    }
}

void heap_push(t_heap *h, int id, long key) {
    if (h->size >= 2) return ;
    h->items[h->size].id = id;
    h->items[h->size].key = key;
    bubble_up(h, h->size);
    h->size++;
}


void heap_pop(t_heap *h) {
    if (h->size == 0) return ;
    h->size--;
    if (h->size > 0) {
        swap_req(&h->items[0], &h->items[h->size]);
        sift_down(h, 0);
    }
}

Why a generic heap if size is always 2?

The subject demands a priority queue. We implement the textbook algorithm so it stays correct for any size. The 2-slot bound just reflects the physical fact that only two neighbors compete for any dongle.

Why the req_less tie-breaker

The subject explicitly requires a deterministic EDF policy "even in edge cases" where two requests have the same deadline. The most common edge case is T=0: every coder has last_compile = sim->start, so every EDF key (last_compile + t_burnout) is identical. Without a tie-breaker, the heap would leave them in thread-scheduler order, which is nondeterministic across runs. Falling back to lower id wins makes the policy reproducible and satisfies the subject.

{

right = i * 2 + 2;

Walk-through of one acquisition

  1. pick_key builds the sort key: arrival time (FIFO) or deadline (EDF).
  2. register_request puts the coder on the low dongle's heap.
  3. wait_for_dongle(low): lock, loop until you're top + available + past cooldown, pop, unlock.
  4. Print has taken a dongle.
  5. Refresh the key, register on the high dongle, wait, take, print.
  6. Any failure path releases what you already hold and returns ERR.
Why sequential (not pre-registering both)? If a coder is parked on dongle B's heap while still waiting on dongle A, they "block" dongle B for everybody else even though B is free. Registering only when we're actually ready to wait keeps the heap honest.

Why cond_timedwait for cooldown?

If you're already at the top of the queue and the dongle is "available" but inside the cooldown window, nobody is going to wake you. We compute the absolute end of the cooldown and sleep exactly until then.

Where last_compile is updated

Right at the start of do_compile, not the end. That matches the subject: "the beginning of their last compile" is the reference point for the burnout deadline.

Why the stagger_start?

Without it, every coder enters acquire_dongles at T+0 and races for dongles at the same instant. Several can succeed at grabbing their low in parallel and then form a long "I hold A, I want B" chain. With N coders that chain can take N cycles to dissolve. The chain is the classic dining-philosophers wait-pattern. Letting even-id (and the last) coders sleep half a compile time before their first attempt splits the field into two groups and caps the chain at roughly N/2 — long enough to never hit the burnout boundary in any realistic configuration.

11. Defense Q&A

Click any question to reveal the answer. Read all of them at least once before the evaluation.

1. Why does each coder need its own thread?
Because every coder acts independently and possibly simultaneously. A thread is the OS abstraction that gives us "an independent line of execution". Without threads, we'd have to write a giant manual scheduler. With them, the OS does the scheduling and our code stays linear.
2. Why a mutex on every dongle?
Two coders could both try to acquire the same dongle at the same time. Both could read available = 1, both could decide to take it, both could set available = 0. That's two coders holding the same physical dongle — impossible. The mutex turns the read-check-set sequence into a single atomic action.
3. Why a condition variable instead of polling with usleep?
Two reasons. CPU cost: a cond_wait thread uses 0 % CPU; a polling loop wastes cycles. Latency: cond_wait wakes the instant another thread signals; usleep can wait up to a full sleep interval before noticing.
4. Why while around cond_wait, not if?
Spurious wakeups exist. Another waiter might have raced you and consumed the resource. Or the condition could have flipped back to false between signal and wakeup. Always re-check after waking.
5. What is a deadlock and how do you prevent one?
A deadlock is a cycle of threads each waiting for a resource the next thread holds. It needs all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption, circular wait. We break the fourth with a resource hierarchy: every coder always grabs the dongle with the smaller id first. See init.c → assign_neighbors.
6. Walk me through what happens when a coder releases a dongle.
  1. release_dongles calls release_one on each dongle.
  2. release_one locks the dongle's mutex, sets available = 1 and last_release = now_us(), then pthread_cond_broadcast.
  3. Every waiter on that condition variable wakes up.
  4. Each one re-runs try_take: am I the top of the heap, is the dongle available, am I past the cooldown? Only the heap's top is allowed to take it.
  5. The winner pops itself from the heap, sets available = 0, returns success. Everyone else goes back to cond_wait.
7. What if a coder is top of the queue but the dongle is in cooldown?
wait_choice detects that case: I am top, dongle is available, but now < last_release + cooldown. We compute the absolute moment cooldown ends via compute_abs and call pthread_cond_timedwait. The thread wakes exactly at that instant (or earlier if someone signals) and retries try_take.
8. How does EDF prevent starvation?
Under EDF the heap key is last_compile + t_burnout — the absolute time at which the coder would burn out. The smaller the key, the closer the deadline, the higher the priority. A coder that has been waiting long has the smallest key and wins the next contest. Provided the parameters are physically feasible, no coder can be passed forever.
9. How is the burnout printed within 10 ms?
A dedicated monitor thread polls every 500 µs. For each coder it reads last_compile (under that coder's mutex) and checks now_us() >= last_compile + t_burnout * 1000. As soon as the deadline is crossed it (a) sets stop = 1, (b) calls force_log("burned out") bypassing the stop check, (c) calls wake_all so no coder is stuck in cond_wait. Worst-case latency is one poll interval ≈ 500 µs, well below 10 ms.
10. How do you stop logs from interleaving?
Every print path (log_state and force_log) holds sim->print_mtx around the printf. Two concurrent print calls serialize on that mutex, so one line never overlaps another.
11. What's your lock order? Could there be a mutex-level deadlock?
The order is:
  • print_mtx is acquired before sim_mtx (inside log_state).
  • dongle.mtx is acquired before sim_mtx (when checking sim_stopped from inside wait_for_dongle).
  • sim_mtx is acquired before coder.mtx (in start_simulation only).
  • For the dongles themselves, the resource hierarchy guarantees they are always taken in ascending id order.
The resulting graph is a DAG (no cycle), so mutex-level deadlock is impossible.
12. What if there's only 1 coder?
There's only 1 dongle. assign_neighbors sets low = high = dongles[0]. The coder takes low successfully, then tries to take high (same dongle, now unavailable) and blocks forever. The monitor eventually detects burnout and ends the simulation. That's the correct behaviour: a single coder physically can't get two dongles.
13. Why a heap if it's always size 2?
The subject requires a priority queue implementation (no STL). I wrote a real binary min-heap with bubble_up / sift_down that works for any size; the storage happens to be 2 because only two neighbors ever compete for a dongle.
14. What memory do you allocate, and how do you guarantee no leaks?
Three mallocs: sim->dongles, sim->coders, sim->threads. All three are freed in sim_destroy, which is called on every exit path of main. Every pthread_mutex_init has a matching pthread_mutex_destroy; every pthread_cond_init has a matching pthread_cond_destroy. Verify with valgrind --leak-check=full.
15. Why do you stamp last_compile at sim start instead of leaving it 0?
Because the monitor reads last_compile the moment it wakes up. If we left it at 0, the deadline would be 0 + t_burnout — already long past, so every coder would be flagged as burnt out at T+0. Stamping last_compile = sim->start for every coder before broadcasting go=1 fixes that.
16. What's a "spurious wakeup" exactly?
pthread_cond_wait is allowed by the POSIX standard to return without anyone having signaled. The kernel may wake a waiter for various reasons (signal delivery, CPU migration, implementation quirks). The standard says: "even with no error, the wait may return". That's why you always check the condition inside a while.
17. What happens during shutdown (success or burnout)?
  1. Monitor sets stop = 1 under sim_mtx.
  2. If burnout: prints the burned out line via force_log.
  3. Calls wake_all which broadcasts sim_cond and every dongle.cond.
  4. Every coder, wherever it was (mid-sleep, mid-wait), checks sim_stopped, releases anything it holds, returns from its routine.
  5. main's join_all completes, sim_destroy tears everything down, exit 0.
18. The evaluator asks you to add an "is idle" state — how?
Add a new function in coder.c: 
static int do_idle(t_coder *c) {
    if (log_state(c, "is idle")) return (ERR);
    return (precise_sleep(c, /* whatever the new arg is */));
}
Insert do_idle(c) wherever they want it in the loop. Add the new time as an argument (bump the argc check in parsing.c). Done in under five minutes.
19. They ask you to switch from EDF to Shortest-Job-First — how?
One line in pick_key: under the new policy, key = t_compile or whatever the new metric is. The heap logic doesn't change.
20. Why no global variables?
The subject explicitly forbids them, and they're a bad idea anyway: globals create hidden coupling, make testing harder, and are a magnet for race conditions. We pass everything explicitly through t_sim, which lives on main's stack.

Q1. How many dongles does a coder need to compile?

The subject says a coder must hold both their left and right dongle at the same time. This is the whole reason for the dining-philosophers analogy: two contended resources per actor.

Q2. Why does each dongle need its own mutex?

Without the mutex, two threads could both observe available == 1 and both decide to take the dongle. The mutex turns the entire check-and-take sequence into a single atomic critical section.

Q3. Why do we wrap pthread_cond_wait in a while loop instead of an if?

POSIX explicitly allows cond_wait to return without a signal (spurious wakeup). Even when signaled, another thread may have raced you. The only safe pattern is always re-check the predicate.

Q4. Which Coffman condition does our resource hierarchy break?

By forcing every coder to acquire the lower-numbered dongle first, we make it impossible to form a cycle of "coder N waits for coder N+1's dongle, which waits for N+2's, ..., which waits for N's". The wait graph becomes a chain, not a cycle.

Q5. Under EDF, what is the heap key for a coder's request?

Earliest Deadline First means: serve the request whose deadline is closest. The deadline of a coder is the moment they would burn out, which is last_compile + t_burnout. Smaller key = earlier deadline = higher priority.

Q6. Why is the per-dongle heap fixed at size 2?

The geometry of the problem caps contention. The heap algorithm itself is generic; the size-2 bound just reflects the physical reality.

Q7. How does the monitor guarantee burnout is printed within 10 ms?

A 500 µs usleep between scans means we can't miss a deadline by more than one poll interval. That's 50 times tighter than the 10 ms tolerance the subject allows.

Q8. Why do we have two loggers, log_state and force_log?

Once the monitor sets stop=1, normal state messages must stop. But the burnout message itself happens after that stop — without force_log bypassing the stop check, the burnout line would never appear.

Q9. Why do even-id coders sleep half a compile time at the start (stagger_start)?

Without the stagger, all N coders grab their low dongle at the same instant and end up queued one-after-another on each others' high dongles — the classic dining-philosophers wait-chain. Splitting them into two waves keeps the chain short.

Q10. Why do we register a coder on a dongle's heap sequentially (low first, then high after low is acquired) instead of pre-registering on both at the start?

The heap must reflect who's actually ready to take the dongle now. If a coder is parked on heap B while waiting on A, they "ghost-reserve" B and starve the other neighbor — that's the EDF bug we caught during testing.

Q11. The evaluator hangs your program. Which is the most likely cause?

Always call wake_all after setting stop = 1. Otherwise threads parked in cond_wait never wake and pthread_join hangs forever. Use gdb -p <pid> + thread apply all bt to confirm.

Q12. Which lock order do we follow in this project?

Every multi-lock code path obeys this partial order. Because the orderings form a DAG (no cycle), there is no possible mutex-level deadlock — completely separate from the resource-hierarchy fix for the dongles themselves.

13. Common bugs & how to debug

"My program hangs forever"

Usually a cond_wait nobody signals. Most likely cause: a stop path that doesn't broadcast every condition variable. Always call wake_all after setting stop = 1.
Debug: gdb -p <pid> then thread apply all bt. Every thread parked in pthread_cond_wait tells you who's stuck.

"Coders burn out instantly at T+0"

You forgot to stamp last_compile = sim->start before broadcasting go=1. The monitor reads last_compile = 0 and decides the coder has been idle since 1970. Fix: inline the last_compile initialization before broadcasting go=1.

"Two log lines on the same physical line"

Either a printf outside print_mtx, or a missing \n. Grep every printf and confirm both.

Helgrind or TSan complains about a race

Some shared variable is read or written without taking the right mutex. Most common offender: reading c->last_compile without c->mtx. Re-walk every critical section.
